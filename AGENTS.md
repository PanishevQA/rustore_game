# AGENTS.md — НЕ СБЕЙСЯ!

This repository is a Unity Android / RuStore game. These instructions are the project contract for coding agents working in this repository.

## 1. Repository reality and source of truth

- Unity project root: UnityProject/
- Pinned Unity Editor: 6000.3.24f1
- The repository default branch main currently does not contain the full Unity project. Do not switch, rebase, or base work on main merely because it is the GitHub default branch.
- Before making changes, verify the current branch contains:
  - UnityProject/ProjectSettings/ProjectVersion.txt
  - UnityProject/Packages/manifest.json
  - UnityProject/Assets/Game/
- For the current development line, codex-local-ui-20260919 is the known full-project base. Task branches may be based on it or on a later branch that contains the same project.
- Never discard existing user changes to make the worktree clean.

Required start-of-task commands:

    git status --short
    git branch --show-current
    git rev-parse --show-toplevel
    Get-Content .\UnityProject\ProjectSettings\ProjectVersion.txt

If the Unity project files are missing, stop changing files and report that the task is on the wrong repository/branch.

## 2. Product constraints

The game is НЕ СБЕЙСЯ!, portrait Android, primarily distributed through RuStore.

Core loop:

see route -> reproduce from memory -> receive score -> challenge a friend

Current release client is offline-first. Do not introduce a mandatory backend dependency for normal gameplay unless the task explicitly requires it.

Gameplay logic must remain independent from RuStore SDKs, ads, analytics, or backend transports. External systems belong behind interfaces/adapters.

Do not add chat, clans, synchronous multiplayer, user-generated levels, battle pass, or other large meta systems unless explicitly requested.

## 3. Architecture

Production code lives under UnityProject/Assets/Game.

Current modules:

- Core -> Game.Core, namespace DontGetSidetracked.Core
- Gameplay -> Game.Gameplay, namespace DontGetSidetracked.Gameplay
- Daily -> Game.Daily
- Social -> Game.Social
- Economy -> Game.Economy
- Monetization -> Game.Monetization
- Analytics -> Game.Analytics

- Services -> Game.Services
- Platform/Android -> Game.Platform.Android, namespace DontGetSidetracked.Platform.Android
- Platform/RuStore -> Game.Platform.RuStore, namespace DontGetSidetracked.Platform.RuStore
- Presentation -> Game.Presentation, namespace DontGetSidetracked.Presentation
- Tests -> Game.Tests

Do not create a duplicate manager/service if an existing service or coordinator already owns the responsibility. Search the repository before adding a new subsystem.

Dependency direction:

- Core gameplay/data classes should be ordinary C# classes where practical.
- MonoBehaviour is primarily for scene binding, input, visual presentation, and Unity lifecycle.
- Platform adapters depend on service abstractions; gameplay must not depend directly on RuStore/Yandex SDK types.
- Presentation may coordinate modules, but domain rules should not migrate into Presentation just to make UI wiring easier.
- Do not use private reflection against GameBootstrap outside the existing GameBootstrapRuntimeBridge contract.
- When adding or moving code across modules, update asmdef references intentionally. Do not solve dependency errors by making everything reference everything.

## 4. Unity assets and serialized data

UnityProject/Assets/Game/Editor/

## 7. Coding rules

Before implementing a feature:

1. search for the current owner classes/interfaces;
2. inspect relevant asmdefs;
3. inspect existing tests;
4. inspect runtime bootstrap/coordinator wiring;
5. make the smallest coherent change.

Prefer deterministic, testable C# for route generation, scoring, economy, save migration/repair, Daily rules, challenge encoding, and policy decisions.

Route generation must preserve the invariant that the same seed + generatorVersion yields the same route across supported devices. Any incompatible generator algorithm change requires a new generator version.

Score is displayed to 0.1%, but underlying logic must preserve current deterministic scoring behavior and tests.

Save format is versioned. Never repurpose old serialized fields in a way that breaks migration. Add migration/repair logic and tests when the schema changes.

Do not store critical progress only in PlayerPrefs.

## 8. Git safety

Before large or risky changes:

- inspect git status --short;
- preserve unrelated existing changes;
- create a checkpoint commit only for already-complete, agent-owned work when appropriate;
- do not silently commit unrelated user changes.

Never:

- force push;
- rewrite public history;
- delete branches as cleanup;
- use git reset --hard against user work;
- remove scenes, ScriptableObjects, or serialized assets unless required by the task.

At completion, report changed files and the validation commands actually run.

## 9. Validation commands

Use the repository wrapper:

    powershell -ExecutionPolicy Bypass -File .\scripts\agent_check.ps1 -Mode Fast
    powershell -ExecutionPolicy Bypass -File .\scripts\agent_check.ps1 -Mode Unity
    powershell -ExecutionPolicy Bypass -File .\scripts\agent_check.ps1 -Mode Full
    powershell -ExecutionPolicy Bypass -File .\scripts\agent_check.ps1 -Mode Build

Modes:

- Fast: repository/static validators + pure C# tests. Use during implementation and after non-Unity logic/documentation changes.
- Unity: Fast checks plus real Unity batchmode compile + EditMode tests + PlayMode startup smoke tests, followed by read-only serialized-project validation of enabled scenes, prefabs, ScriptableObjects, materials, missing scripts, and broken object references. This is the normal final gate for C#, asmdef, scene/editor tooling, gameplay, UI wiring, and serialized project changes.
- Full: Unity gate plus release-readiness preparation/report. Use for Android, RuStore, Yandex Ads, manifests, packages, signing/build configuration, release tooling, or when explicitly preparing a release candidate.
- Build: Full gate plus the existing ProductionAndroidBuild batchmode entrypoint and post-build release metadata/SHA-256 verification. Use only when an actual production AAB is requested; this mode requires a correctly configured Android SDK, signing setup, and release-ready RuStore dependencies.

The existing underlying Unity runner is:

scripts/run_release_candidate_checks.ps1

It writes Unity logs/results under:

artifacts/release-candidate/

Serialized-project validation additionally writes:

- artifacts/release-candidate/serialized-validation.log
- artifacts/agent-check/unity-serialized-validation.txt

Agent wrapper logs belong under:

artifacts/agent-check/

Do not claim Unity compilation passed if only Python/static checks were run.

### Self-hosted Unity feedback loop

When repository variable UNITY_SELF_HOSTED_ENABLED is true and a runner with labels self-hosted/windows/x64/unity is online, pushes to trusted agent/** branches automatically execute the real Unity gate. Manual workflow dispatch exposes Unity, Full, and Build choices; push events always use Unity mode. The workflow must never be changed to run on pull_request or pull_request_target while this repository is public.

## 11. Scene / prefab / UI automation policy

For repetitive hierarchy/component wiring, create or extend an Editor command instead of instructing the human to click through the Inspector.

A scene/UI task is not complete merely because C# compiles. The agent should verify, as applicable:

- required GameObjects/components exist;
- serialized references are assigned;
- only intended owners control each screen/surface;
- scene can be opened/imported by Unity batchmode without new errors;
- existing release UI validators still pass;
- DontGetSidetracked.EditorTools.AgentProjectValidator.ValidateForAutomation passes without missing scripts or broken serialized references.

The serialized validator is read-only: it may open build scenes and prefab contents for inspection, but it must restore the original scene setup and must not save scenes/prefabs/assets.

Avoid Computer Use/click automation when the same result can be produced through UnityEditor APIs.

## 13. Images and generated visual assets

Coding agent capabilities and image generation are separate.

The coding agent may import provided images, configure import settings, slice sprites, create materials, assign images to UI, and create deterministic editor tooling for asset import.

Do not pretend the coding agent generated a visual asset if no image-generation capability was actually used.

Generated visual assets should be imported through a clear source/derived-asset workflow and validated in Unity after import.

## 14. Failure handling loop

For implementation tasks, use this loop:

1. inspect;
2. plan;
3. change;
4. run the cheapest relevant checks;
5. run the required final Unity gate;
6. read failing logs/results;
7. fix the actual cause;
8. repeat validation;
9. report only the final status and any external blocker.

On Unity failure, inspect at minimum:

- artifacts/release-candidate/editmode.log
- artifacts/release-candidate/editmode-results.xml
- artifacts/release-candidate/playmode.log
- artifacts/release-candidate/playmode-results.xml
- artifacts/release-candidate/serialized-validation.log
- artifacts/agent-check/unity-serialized-validation.txt
- artifacts/release-candidate/readiness.log when Full mode was used
- artifacts/release-candidate/release-readiness.txt when produced
- artifacts/agent-check/unity-diagnostics.json for the structured compiler/exception/test summary produced after a failed Unity gate

Do not stop after the first compiler error if it is fixable within the repository.

## 15. Definition of Done

A coding task is complete only when all applicable items are true:

1. requested behavior is implemented and wired into the existing architecture;
2. no duplicate subsystem was introduced without justification;
3. changed code respects asmdef/module boundaries;
4. required assets/scenes/serialized references are intact and the serialized-project validator passes for scene/prefab/UI/material/ScriptableObject changes;
5. relevant automated tests were added/updated;
6. relevant static validators pass;
7. for Unity-affecting work, agent_check.ps1 -Mode Unity passes;
8. for release/platform/package work, agent_check.ps1 -Mode Full passes or a clearly external production-only blocker is documented;
9. no new Unity Console/compiler errors are present in the batchmode log;
10. no unrelated user changes were overwritten;
11. changed files and executed validation commands are reported.

A task is not complete because files were merely created or because static text inspection looks correct.

## 16. Scope-specific checks

If the task touches server/, also run its existing backend tests rather than assuming the Unity checks cover it.

If the task touches RuStore/Yandex/package/build configuration, inspect the current official vendor documentation before changing versions or integration contracts.

If the task touches a new scene/prefab creation workflow, prefer adding an Editor validation command so future agents can verify the serialized result without manual Inspector review.
